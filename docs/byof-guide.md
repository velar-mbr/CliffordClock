# Bring your own field

This is the guide for adapting CliffordClock to *your* trap: export a
field grid from your own FEA/CAD tool, get a metrology shift report. The
companion pieces are `examples/realistic_lattice_sr87.yaml` (a runnable
example built on a physically plausible, not measured, stray-field
scenario, generated by `examples/generate_patch_field.py`) and
`notebooks/04_bring_your_own_field.ipynb` (the adaptation template: load
your CSV, inspect/smooth it, run, interpret the report). Read this guide
first; the notebook is the copy-and-edit starting point.

## CSV format contract

`cliffordclock.fields.load_field_csv` (`docs/fields.md` has the full API):

```
x,y,z,Ex,Ey,Ez
-0.001,-0.001,-0.001,123.4,-56.7,8.9
...
```

- Header row required; the six columns may appear in any order, looked up
  by name, so column order in your export does not matter.
- **Units** (CONVENTIONS.md section 10, SI at every API boundary):
  positions in **meters**, field components in **V/m**. If your FEA tool
  exports mm, kV/cm, Gaussian units, or anything else, convert before
  writing the CSV: `load_field_csv` does not do unit conversion, and a
  missed conversion silently produces a report off by whatever factor you
  dropped.
- One row per sample point. Points forming the complete Cartesian product
  of three axes (`grid.regular == True`) get the fast/simple RBF-on-a-grid
  path; anything else is accepted as a scattered point cloud
  (`grid.regular == False`). `FieldSmoother.fit` handles both
  identically, since the RBF fit does not require a regular grid, but a
  scattered cloud makes it harder to eyeball whether your export actually
  resolves the field's structure (see "Grid spacing" below).
- Rejected outright (`ValueError`, not silently coerced): missing/empty
  file, missing required column(s), a non-numeric cell, a short/malformed
  data row, a non-finite (NaN/Inf) coordinate or field value, or two rows
  with the exact same `(x, y, z)` coordinates, **unconditionally, even
  when their field values agree** (FEA exports commonly emit benign
  duplicate rows at mesh boundaries; deduplicate before import, e.g.
  `df.drop_duplicates(subset=["x","y","z"])`). *Near*-duplicate points
  (distinct but closer than ~1e-9 × the domain diagonal) raise only when
  their values disagree, and warn otherwise: see the warnings table
  below and `load_field_csv`'s docstring for the complete list.

## COMSOL exports

If your FEA tool is COMSOL, `cliffordclock.fields.load_field_comsol`
(`docs/fields.md` has the full API) reads its native "Spreadsheet" export
format directly, with no manual CSV conversion needed.

**Export dialog settings.** In COMSOL, `Results > Export > Data`:

1. **Data format: "Spreadsheet"** (not "Sectionwise", a
   different, unsupported format; this loader detects and rejects it with
   a clear error rather than silently mis-parsing it). File extension
   `.txt`, `.csv`, or `.dat` all work; comma- and whitespace-delimited
   variants are both accepted.
2. **Expressions:** the three Cartesian components of your field, e.g.
   `es.Ex`, `es.Ey`, `es.Ez` for the built-in Electrostatics interface (if
   your model uses a renamed or non-default interface, pass its prefix as
   `load_field_comsol(..., expression_prefix="yourprefix")`).
3. **A single, non-parameterized (non-swept) static study.** If your model
   has a parameter sweep (frequency, voltage, geometry, ...), export one
   parameter value at a time: a header carrying an `@ param=value` tag is
   explicitly out of scope (out of scope: no parameter-sweep/multi-
   dataset files) and raises a clear error rather than picking one
   dataset arbitrarily.
4. **A 3D model/study.** 2D exports (`% Dimension: 2`) are rejected; this
   tool's whole physics stack (CONVENTIONS.md) is 3D.
5. **Units:** the loader converts length (`m`, `mm`, `cm`) and field
   (`V/m`, `kV/m`, `V/cm`) units automatically from what COMSOL's export
   dialog writes into the header, so pick whichever of these your model
   uses natively; no manual conversion needed. Any other unit (a
   different physical quantity, an unsupported unit string) raises a
   `ValueError` naming it, rather than a silent wrong-factor conversion.

**`.mphtxt` is a different format.** COMSOL's `File > Export > Mesh`
(`.mphtxt`) and `Results > Export > Image/Animation` outputs are *not*
what this loader reads: only `Results > Export > Data` with the
Spreadsheet format above works. Pointing `load_field_comsol` at a
`.mphtxt` mesh file (or any file whose first line does not start with
`%`) raises a clear "does not look like a COMSOL Spreadsheet export"
error rather than attempting to parse mesh topology as field data.

**Config usage (`field.comsol`).** Point `field.comsol` at your export
path (`docs/cli.md`'s "Field sources" section has the full schema); it
loads and fits a `FieldSmoother` exactly the way `field.csv` does
(`field.smoothing` applies the same way):

```yaml
field:
  comsol: my_export.txt
  # expression_prefix: es   # optional (default "es"); set this if your
  #                          # COMSOL model renamed the Electrostatics
  #                          # physics interface
  smoothing: 0.0
```

`examples/comsol_electrode_sr87.yaml` is a runnable worked example built
on `examples/generate_fd_electrode_field.py` /
`examples/fd_electrode_field.txt`, a from-scratch finite-difference
electrostatics solve, written out in COMSOL Spreadsheet format and loaded
back through this exact `field.comsol` config path. Use it as a template
for sanity-checking your own export the same way: run it, evaluate at a
point where you also have an independent back-of-envelope estimate, and
compare.

**Python API, for notebooks/scripts.** The loader is also available
directly, without going through `config.yaml`:

```python
from cliffordclock.fields import load_field_comsol, FieldSmoother

grid = load_field_comsol("my_export.txt")
smoother = FieldSmoother.fit(grid)
E, grad_E = smoother.evaluate(pos)
```

## Grid spacing vs. feature size

`FieldSmoother.fit` (CONVENTIONS.md E11-E13) splits your field into a
degree-1 (uniform + linear) analytical baseline plus a thin-plate-spline
RBF residual fitted through every point in your CSV. The RBF can only
resolve field structure your grid actually samples: if your field has a
real feature (a patch potential, an electrode edge, a sharp gradient near
a boundary) with characteristic length scale `L`, your grid spacing should
be a fraction of `L`: as a rule of thumb, several samples across the
smallest feature you care about resolving, not just one or two. Too coarse
a grid does not fail loudly; it silently under-resolves the feature and
the RBF interpolates a smoother field than the real one.

`examples/patch_field_sr87.csv` (`examples/generate_patch_field.py`)
demonstrates the other end of this trade-off deliberately: it samples a
17x17x17 grid (spacing ~31 um) over a 500 um domain against 8 mm-scale
patch features, more than 250x oversampled relative to the feature
scale, because the demo prioritizes a clean, unambiguous fit over grid
economy. Your own export does not need to be this generous; it needs to
resolve *your* field's actual features.

Two practical constraints on grid size:

- **`FieldSmoother.MAX_FIT_POINTS` (20,000).** The RBF fit solves a dense
  `(N, N)` linear system, an `O(N^3)` operation. Larger point clouds
  raise `ValueError` outright; downsample (or subsample a region of
  interest) rather than exporting your entire mesh.
- **Fit wall time in practice.** `examples/patch_field_sr87.csv`'s 4913
  points fit and evaluate in a couple of seconds; larger grids (several
  thousand points) can start to dominate a `cliffordclock run`'s wall time well
  before `MAX_FIT_POINTS`'s hard cap. If your own export is large, export
  only the region around the trap you actually need (see "Scope today"
  below on the ~mm-to-cm domain this tool targets) rather
  than a whole chamber's mesh.

## `smoothing`: guidance for noisy exports

`field.smoothing` (`FieldSmoother.fit`'s `smoothing` parameter) adds
Tikhonov regularization to the RBF linear system:

- **`smoothing: 0.0`** (the default) fits the residual *exactly* at every
  data point, appropriate for clean, simulated data (an FEA solve with
  no measurement noise, like `examples/patch_field_sr87.csv`).
- **`smoothing > 0`** trades exact interpolation for robustness. Use this
  when your export carries genuine noise (a measured field, or an FEA
  mesh with numerical solver noise): fitting noisy data exactly forces
  the RBF to chase the noise between points, producing a wild, physically
  meaningless interpolant between samples. A small nonzero `smoothing`
  (start around `1e-8`-`1e-6` relative to your field's characteristic
  magnitude squared, and increase if the fit still looks noisy when
  plotted per notebook 04's section 2) lets the fit trade a little
  accuracy at the sample points for a much smoother, more physically
  plausible interpolant between them.
- `smoothing` is also the fix for `IllConditionedFitWarning` below, even
  on otherwise-clean data.

## Warnings you may see

| Warning | Module | Cause | What to do |
|---|---|---|---|
| `NearDuplicatePointsWarning` | `cliffordclock.fields.io` | Two sample points sit far closer together (default: within `1e-9` times the bounding-box diagonal) than the domain scale suggests any two *distinct* points should. Common cause: mesh refinement placed two nodes almost on top of each other, or export tooling round-tripped coordinates through single precision. | Usually harmless to the physics (if the two points also report matching field values) but a sign your export has redundant/degenerate sampling; consider deduplicating. If the two near-duplicate points report **disagreeing** field values, `load_field_csv`/`FieldSmoother.fit` raise `ValueError` instead of warning, since that is corrupted or inconsistent input, not noise. |
| `IllConditionedFitWarning` | `cliffordclock.fields.smoother` | The RBF kernel matrix's estimated reciprocal condition number (`rcond`) has dropped below `1e-12`. fp64 has ~15-16 decimal digits, so a system this poorly conditioned returns fitted coefficients dominated by numerical noise, not your actual field data, even though the linear solve "succeeds" with no exception. Near-duplicate points are the most common cause (two RBF basis functions become nearly linearly dependent). | Increase `smoothing` (see above), or clean up near-duplicate points in your export. |
| `OutOfBoundsWarning` | `cliffordclock.fields.smoother` | `FieldSmoother.evaluate` was queried outside your CSV's bounding box. The fit is still evaluated (extrapolated, not interpolated) and a value is still returned, but nothing constrains the RBF/baseline sum's behavior outside the convex hull of your data, so it should not be trusted the way an interior value is. | Make sure your CSV's domain actually covers where your ensemble's atoms/quadrature nodes sit: notebook 04's section 1 prints the bounding box; compare it against your trap's motional extent (`docs/timescales.md` has typical numbers). |

`notebooks/04_bring_your_own_field.ipynb`'s section 6 reproduces the first
two warnings live on a small synthetic example, including the
`smoothing`-as-fix demonstration.

## Adapting the example

1. Export your field to CSV (above) and drop it somewhere under `examples/`
   (or point at it directly with an absolute/relative path).
2. Copy `examples/realistic_lattice_sr87.yaml`; change `field.csv` to your
   file's path, `trap.omega_xyz`/`center` to your trap's parameters, and
   `species` to your clock species (`docs/cli.md` has the full
   `config.yaml` schema).
3. `coupling.type: stark_dc` (E14b, `docs/coupling.md`) works out of the
   box for `Sr87`/`Yb171` (registry-resolved `Delta_alpha`); for another
   species, supply `coupling.delta_alpha_dc_si` or
   `coupling.stark_coefficient_hz_per_v2_m2` explicitly.
4. `cliffordclock run your_config.yaml --output-dir /tmp/out` (from the repo root,
   so relative CSV paths resolve the way the shipped examples' do), or
   adapt `notebooks/04_bring_your_own_field.ipynb` cell by cell: its
   "REPLACE THIS CELL" markers are exactly steps 1-3 above.
5. Read `report.json`'s `mean_fractional_shift`/`shift_std_error`/
   `t2_star_s` per notebook 04's section 5, and check
   `uncertainty_notes` for the resolved coupling coefficient's provenance
   and (for `fast_path` runs) the E29 scope caveat below.

## Scope today

The bring-your-own-field path accepts CSV and COMSOL's "Spreadsheet"
text export (`field.comsol` in `config.yaml`, see "COMSOL exports"
above); most other FEA tools can dump a tabulated field on a grid or
point cloud that converts to the CSV contract directly. It models the
CONVENTIONS.md E14b scalar DC-Stark term (quadratic DC-Stark, scalar
polarizability) plus the E21 kinematic second-order Doppler term, with
`Sr87` and `Yb171` resolved from the species registry
(`cliffordclock.ensemble.species`) and any other species usable through
an explicit `coupling.delta_alpha_dc_si` or
`coupling.stark_coefficient_hz_per_v2_m2` override; `docs/coupling.md`
has the full physics scope statement, and `docs/roadmap.md` covers what
comes next (VTK and native-FEA import, AC-Stark and magnetic-field
systematics, tensor-polarizability species like `Al27+`, and a modeled
uncertainty budget beyond `uncertainty_notes`' free-text provenance).

One scope boundary is worth keeping in view while reading results: the
lattice fast path (E29, the default for `ensemble.regime: lattice`)
reports the Stark/field shift from its static (`v=0`) quadrature nodes,
which by construction carry no motional second-order Doppler
contribution. `docs/validation.md`'s KA4 case computes that
systematic separately, for a classical ensemble, via
`integration.mode: secular`; a `fast_path` run's
`report.uncertainty_notes` states this scope directly, and it is the one
caveat to repeat wherever you quote a `fast_path` number.
