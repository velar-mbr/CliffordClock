# Dataset benchmark results: NIST/JILA/NPL/USTC public data

## Executive summary (start here)

**What was compared:** this engine's `coupling.type: stark_dc` (DC-Stark,
CONVENTIONS.md E14b) pipeline against every DC-Stark-relevant row in six
publicly authorized sources: a JILA Sr-87 lattice-clock paper
(arXiv:2403.10664) and its PRL Supplemental Material, a NIST phase/Allan-
deviation dataset (DOI 10.18434/M32206), an NPL Rydberg-electrometry paper
(arXiv:1706.01944), a USTC Sr-1 clock evaluation (Metrologia 63, 025002),
and one further USTC-cited paper this project could not access (Metrologia
61, 015006).

**The reproducibility headline (owner-ratified 2026-08-11): TWO
reproducibility cases MET: NPL stray-field (below) and the Bothwell
mm-scale gravitational-redshift case (its own section at the end of
this document; `benchmarks/run_bothwell_redshift.py`). Zero blind
predictions, unchanged.** `benchmarks/results/wp10_results.json`'s
`kpi_summary` ("1 of 1") remains a frozen artifact of the WP10
protocol, counting only that pass's sources; the project headline is
the two-case statement above.

**The NPL result:** the first case where an independent, publicly measured
stray field could be run through this engine's pipeline. The predicted
DC-Stark shift band overlaps NPL's own published band: **MET**. This is
a *reproducibility* check (NPL had already combined the same two published
ingredients), not a blind prediction.

**Classification taxonomy (binding) used throughout:** `"reproducibility"`
(independently-sourced inputs, engine output checked against a published
result already derived from those inputs, the NPL case), `"blind_prediction"`
(an engine prediction checked against a measurement the engine's own
inputs did not already combine, currently empty, a genuine open gap, not
a modeling failure), `"not_applicable"` (the physics or data category
is outside this engine's scope, or the source lacks an independent field
input, 13 of 14 rows considered), `"arithmetic_reproduction"` (a
published *row that is itself computed*, not independently measured, run
back through this engine's own formula/coefficients, the JILA BBR case
below; explicitly weaker than `"reproducibility"`, since nothing
independent of the engine's own inputs is being checked against), and
`"cross_vintage_comparison"` (an engine prediction built from an
INDEPENDENT input, typically a different vintage/method's theory or
measurement of the same quantity, checked against a published result
that input was never combined with, but where the *other* ingredient of
that published result (e.g. its own applied field or gradient) still
traces to the source's own trap-model/apparatus calibration rather than a
fully independent measurement, the Roos quadrupole-slope case below.
Weaker than `"blind_prediction"` for that reason (a genuine
blind-prediction case would need every ingredient on both sides to be
independent of every other), but a real external comparison, distinct
from `"arithmetic_reproduction"`'s circularity (the compared-against
quantity was never derived from the same input being used to predict it).

**Audit trail:** every number below is reproducible from committed
fixtures via `python benchmarks/run_benchmarks.py`; sources, checksums,
and access logs are in `benchmarks/SOURCES.md`; the per-row scope
reasoning is in `benchmarks/MAPPING.md`.

## Reproducibility case: NPL arXiv:1706.01944 (Sr87 DC Stark): the main event

**Verdict: MET.** This is the first case across all of this benchmark's passes
where every pipeline input traces to an independent publication and the
resulting predicted band can be meaningfully compared to a published band.

### What was extracted, and where (independently re-verified, not trusted from the dossier)

An internal research dossier (not part of this distribution) first
identified these values as a candidate source; this session re-fetched
arXiv:1706.01944v1 and independently re-extracted them from the raw PDF
text before using them for anything:

- **Residual field** (Section IV, the paragraph beginning "Next the
  external field was switched off..."): *"A fit to the resulting
  splitting revealed a residual electric field of 1.52
  +0.62(stat)/-0.22(stat) +0.05(sys)/-0.03(sys) V m⁻¹ most likely due to
  patch potential on the surrounding chamber."* Measured via Rydberg-
  state EIT spectroscopy, independent of the clock transition itself.
- **Published clock shift** (same section, next paragraph): *"Translating
  this electric field and corresponding uncertainty to the DC Stark
  shift of the ¹S₀-³P₀ clock transition results in a fractional
  frequency shift of -1.6 (+0.4/-1.6) x 10⁻²⁰."*
- **Δα provenance**: reference [3], cited in the introduction's sanity-
  check example ("an electric field of 570 V/m yields a DC Stark shift
  of 1 Hz [3]"), is **T. Middelmann, S. Falke, C. Lisdat, U. Sterr,
  Phys. Rev. Lett. 109, 263004 (2012)**, the exact paper this project's
  `Sr87` species registry entry already cites. Independently
  cross-checked by running this project's own pipeline at
  570 V/m predicts `-2.3297e-15` fractional = `-0.99997 Hz`, which rounds
  to the paper's own quoted "1 Hz."

Full citation table and access log: `benchmarks/SOURCES.md` section 4.

### Why this is a "reproducibility" case, not a "blind prediction" (binding label)

NPL measured their field independently of the clock transition, then
converted it to a shift using the same published `Δα` this project's
registry uses. **NPL already combined the same two ingredients this
engine's pipeline combines.** Running `coupling.type: stark_dc` on their
field with the registry's `Δα` therefore reconstructs a number NPL had
already computed themselves; it demonstrates end-to-end pipeline
correctness against two independently published inputs/outputs with no
fitting anywhere in the chain (a real, falsifiable claim: a sign error,
unit-conversion bug, or wrong `Δα`-to-`k_S` derivation would show up as a
non-overlapping band), but it does **not** demonstrate that this engine
predicts a clock shift nobody had already computed. This document and
`benchmarks/MAPPING.md` never describe this case as "validated against
an independent measurement of the shift": that framing would imply a
blind prediction, which this is not. `case_class` in the JSON output is
literally the string `"reproducibility"`, structurally separate from
`"blind_prediction"` (still empty).

### Method: propagating asymmetric uncertainty (no Gaussian pretense)

NPL's field has independent, individually asymmetric statistical
(`+0.62/-0.22`) and systematic (`+0.05/-0.03`) uncertainties. Per the
binding instruction to avoid any Gaussian assumption on asymmetric
errors, `benchmarks/loaders.AsymmetricMeasurement` combines stat+sys **in
quadrature, separately on each side** (never symmetrizing the two sides
against each other):

```
E_lo      = 1.52 - sqrt(0.22^2 + 0.03^2) = 1.2980 V/m
E_nominal = 1.52 V/m
E_hi      = 1.52 + sqrt(0.62^2 + 0.05^2) = 2.1420 V/m
```

`benchmarks/run_benchmarks.run_npl_reproducibility_case` runs the real
pipeline **three separate times** (`species: Sr87`, `coupling.type:
stark_dc`, lattice fast path, `n_quad=1` uniform field, 1 s
interrogation, the same machinery `tests/test_known_answers.py`'s KA1
validates) at `E_lo`, `E_nominal`, `E_hi`, not an algebraic shortcut.
Because E14b's shift is `-(k_S)|E|²/ν0` (monotonic in `|E|`), the
predicted band's own asymmetry is inherited through the pipeline from the
field's asymmetry, not hand-constructed; monotonicity is asserted at
runtime, not assumed.

| Field (V/m) | 1.2980 | 1.5200 | 2.1420 |
| Predicted Δν/ν₀ (this engine) | -3.2900×10⁻²⁰ | -1.6567×10⁻²⁰ | -1.2080×10⁻²⁰ |

**Overlap test** (`benchmarks/run_benchmarks._bands_overlap`, precisely
defined: two closed intervals `[lo1,hi1]`/`[lo2,hi2]` overlap iff
`lo1 <= hi2 and lo2 <= hi1`; unit-tested,
`tests/test_benchmarks_loaders.py::test_bands_overlap_precise_definition`,

bands **overlap**: NPL's published band `[-3.2, -1.2]×10⁻²⁰` sits
almost entirely inside this engine's predicted band `[-3.290,
-1.208]×10⁻²⁰`, and each band's own nominal value falls inside the
other's band (predicted nominal `-1.657×10⁻²⁰` is inside NPL's
`[-3.2,-1.2]×10⁻²⁰`; NPL's nominal `-1.6×10⁻²⁰` is inside the predicted
`[-3.290,-1.208]×10⁻²⁰`). **`kpi_verdict = "MET"`.**

## Arithmetic-reproduction case: JILA BBR row (arXiv:2403.10664 Table I "BBR")

**Verdict: MET** (`case_class = "arithmetic_reproduction"`), but read the

case is WP20's benchmark-case candidate
(WP20 design item 5, gate edit 8), generated
by a separate committed script,
`benchmarks/run_bbr_jila_arithmetic_reproduction.py`
(`python benchmarks/run_bbr_jila_arithmetic_reproduction.py` regenerates
`benchmarks/results/wp20_bbr_arithmetic_reproduction.json`/`.md`), and
kept structurally and numerically separate from this document's WP10
`kpi_summary` totals above (still `1` reproducibility case, `0`
blind-prediction cases, `13` not-applicable rows, `14` total, unchanged
by this addendum).

### Why this is "arithmetic reproduction", not "reproducibility" (binding label, G7 sign-off B5)

The project's theory sign-off record (G7) B5 (ratified): **"arithmetic
reproduction of a published standard-formula evaluation"**, explicitly
a *weaker* class than the NPL case's `"reproducibility"` label above.

- **NPL's case (above):** the field NPL fed into the DC-Stark formula was
  measured **independently of the clock transition** (Rydberg-EIT
  spectroscopy on a different atomic state, a different apparatus
  measurement from the shift itself).
- **This case:** JILA's own BBR row is **itself computed**: their own
  measured operating temperature (`T = 293.282(4) K`, in-vacuum RTDs) run
  through the same standard BBR formula (E32/CONVENTIONS.md, identical in
  structure to Beloy et al. PRL 113, 260801 (2014)/Middelmann et al. PRL
  109, 263004 (2012)) using their own fitted/measured coefficients.
  Nothing about JILA's *own* published shift is an independent
  measurement the way NPL's field was; reproducing it arithmetically
  checks this engine's formula-and-coefficient arithmetic and provenance
  chain, not independent BBR physics.
- **Expected almost by construction.** The registry's Sr87 dynamic
  polynomial (`cliffordclock.ensemble.species.SR87.bbr_coefficients`,
  `dyn_coeffs_hz={6: -0.13216, 8: -0.01231, 10: -0.00858}`) is the
  PTB-2025 rescaling (arXiv:2507.14030) of Lisdat et al.'s fit *shape*
  (PR Research 3, L042036 (2021)), renormalized to **JILA's own**
  `-153.06(33) mHz` dynamic-term anchor at 300 K (Aeppli et al.
  arXiv:2403.10664). Close agreement between this engine's prediction and
  JILA's own row is therefore expected almost by construction, not a
  surprising independent success; see the project's theory sign-off
  record (G7)
  B5/B2 for the ratified reasoning. This case demonstrates the engine's
  **arithmetic and provenance chain end-to-end**, not a new physics
  validation. Any `1e-19`-class number quoted here is
  **"arithmetic-reproduction fidelity", never "BBR accuracy"** (G7
  sign-off A4#2c).

### Method: only the pinned registry polynomial, via the real engine functions

Per the WP20 gate's binding requirement (gate edit 8): this case re-runs
an earlier quick single-`T^6` estimate from this project's internal
review (which found a `~0.04%`
residual) with the **pinned registry polynomial** (`T^6`+`T^8`+`T^10`,
not a single term), calling the real engine functions,
`cliffordclock.integrator.omega.bbr_pivot_perturbation`/
`bbr_pivot_uncertainty`, directly, with no hand arithmetic feeding any
reported number:

1. Resolve `Sr87` from the species registry (pinned PTB-2025 rescaled
   dynamic polynomial + Middelmann static term, both citation-traced in
   the registry docstring).
2. `bbr_pivot_perturbation(293.282, Sr87)`: the nominal prediction.
3. `bbr_pivot_perturbation` again at `293.282 - 0.004` and
   `293.282 + 0.004` K (JILA's own published `4.1 mK` temperature
   uncertainty): two more direct engine calls, giving the **temperature
   band**.
4. `bbr_pivot_uncertainty(293.282, Sr87)` (no temperature-uncertainty
   argument): the registry **coefficient-uncertainty band**.
5. `bbr_pivot_uncertainty(293.282, Sr87, 0.004)`: coefficient and
   temperature uncertainty combined in quadrature by the engine itself;
   this combined band is what is compared against JILA's own published
   band via the same closed-interval overlap test NPL's case uses
   (`run_benchmarks._bands_overlap`, reused, not reimplemented).

**Interpretation.** The residual is about 33× smaller than the combined
uncertainty band's half-width (`2.25×10⁻²⁰` vs `7.36×10⁻¹⁹`), and the
predicted and published bands overlap comfortably, consistent with the
"expected almost by construction" framing above (the registry polynomial
is anchored to this exact JILA number). **This is not a finding of an
anomaly**: re-running the arithmetic with the pinned `T^6+T^8+T^10`
registry polynomial (per gate edit 8), instead of the earlier
single-`T^6` quick estimate from this project's internal review (which
found a `~0.04%`/`~2×10⁻¹⁸` residual), reduces the residual by
roughly two orders of magnitude (~100×), to `~2.25×10⁻²⁰`, exactly the outcome
expected once the full polynomial (rather than a truncated one-term
scaling) is used, since the polynomial was rescaled against this same
JILA value in the first place. Had the residual instead *exceeded* the
combined bands, that would have been reported here as a genuine finding
(most likely the static-coefficient vintage or higher-order `T^8`/`T^10`
shape sensitivity at `293 K`); it does not, so none is reported.

## Cross-vintage comparison: Roos et al. quadrupole slope (quant-ph/0701215v1)

**Two variants, both `case_class` values distinct from `"reproducibility"`
and `"blind_prediction"` above, generated by a separate committed
script, `benchmarks/run_roos_quadrupole_slope.py`
(`python benchmarks/run_roos_quadrupole_slope.py` regenerates
`benchmarks/results/roos_quadrupole_slope.json`/`.md`), and kept
structurally and numerically separate from this document's WP10
`kpi_summary` totals above (still `1` reproducibility case, `0`
blind-prediction cases, unchanged by this addendum, same as the BBR
addendum above).**

Roos et al. (quant-ph/0701215v1, published Nature 443, 316 (2006))
prepared a two-ion entangled state, Psi_1 =
(|-5/2>|+3/2> + |-1/2>|-1/2>)/sqrt(2), and measured its quadrupole-shift
parity-oscillation frequency against an applied, mechanically
(omega_z-)calibrated axial electric-field gradient, fitting a straight
line (Fig. 4a): slope `a = 2.975(2) Hz*mm^2/V` over `dE_z/dz = 12-48
V/mm^2` at beta=0, offset `Delta_0/(2*pi) = -2.4(1) Hz`. This case
predicts that slope from this engine's real quadrupole-shift functions
(`cliffordclock.integrator.omega.quadrupole_shift_joules`/
`quadrupole_mj_factor`) and the species registry's Ca+:D5/2 entry
(`cliffordclock.ensemble.species.QUADRUPOLE_MOMENTS["Ca+:D5/2"]`), two
ways.

### Why two variants, and which one leads (binding label, G8 sign-off B4)

The project's theory sign-off record (G8) B4 ratified this exact
labeling discipline for the analogous Barwood benchmark case; this Roos
case applies it identically:

- **Headline: cross-vintage comparison.** Predicting Roos's slope from
  Itano's INDEPENDENT theory value, `Theta_theory(Ca+:D5/2) = 1.917
  ea0^2` (Itano, Phys. Rev. A 73, 022510 (2006), no published
  uncertainty), a different vintage and a different method (ab-initio
  calculation) from Roos's own 2006 measurement. This is a genuine
  external comparison: neither the theory Theta nor its citation traces
  back to the Fig. 4a fit being predicted.
- **Secondary: arithmetic reproduction.** Predicting Roos's slope from
  Roos's OWN extracted `Theta = 1.83(1) ea0^2`, the very number their
  own paper derives BY INVERTING their own Fig. 4a fit through
  `Theta = (5/12)*h*a`. Using it to predict the same fit's slope is
  circular by construction: not an external check, only a closed-loop
  arithmetic/factor-consistency check of this engine's chain against
  Roos's own published conversion relation.
- **Even Roos's own gradient is not independent of a trap model** (G8 B4's
  second nuance, applying here as it did to Barwood): `dE_z/dz` is
  calibrated from the ion's own measured axial secular frequency `omega_z`
  via `dE_z/dz = -m*omega_z^2/e`, a direct mechanical measurement, but
  still trap-model-derived, not an FEA-independent field reconstruction.
  So even the cross-vintage variant is not a fully independent-gradient
  validation; it is bounded, like every cross-vintage comparison in this
  document, by both sides' own uncertainty, not a precision validation.

### Structural pin: the 24/5 two-ion enhancement

Before either slope variant, the derivation's structural spine is pinned
directly from real engine calls: the two-ion Psi_1 splitting, at the
doubled gradient each ion sees from its partner (Roos p.5-6: "the
presence of a second ion doubles the electric field gradient at the
location of the other ion"), is `+24/5 = +4.8` times a single `|-5/2>`
ion's shift at the same *applied* (undoubled) gradient, exactly Roos's
stated "24/5 enhancement." `tests/test_roos_benchmark.py` pins this at
float precision, computed from `quadrupole_shift_joules`/
`quadrupole_mj_factor`, never hand arithmetic.

| Predicted \|a_pred\| | 3.115229 Hz*mm^2/V | 2.973849 Hz*mm^2/V |
| Predicted band | (no Theta uncertainty to propagate) | [2.957599, 2.990100] Hz*mm^2/V |

## Reproducibility case: Bothwell et al. mm-scale gravitational redshift (Nature 602, 420 (2022) / arXiv:2109.12238)

**Trigger:** WP22, beta gate,
owner trigger after reviewing the Fortier/Luiten/Margolis survey (Optica
13, 143 (2026)): the tool's dispersion observables should land on the
mainstream lattice-clock frontier, mm-scale extended samples, not only
the chamber-scale showcase. G9 theory sign-off,
the project's theory sign-off record (G9), Part B.

Bothwell et al. measured the gravitational redshift gradient across a
millimetre-scale 87-Sr optical-lattice sample, the first single-
apparatus measurement of General Relativity's gravitational time dilation
at this length scale, and (unlike the NPL case's classical-Stark-shift
reconstruction) a genuinely relativistic observable. `benchmarks/run_bothwell_redshift.py`
configures the REAL `ensemble.regime: lattice_extended` pipeline (WP22
Part 2) to their sample geometry and lets the actual extended-sample
machinery (per-site geometry, Gaussian-envelope weighting, per-site E36
pivot evaluation, weighted-least-squares map fit) predict the per-site
slope end to end, with zero adjustable inputs.

### Why this is a "reproducibility" case, not a "blind prediction" (and
its inverted-NPL caveat, binding label, G9 sign-off B4)

Structurally the SAME class as the NPL case: this engine + a published
local gravity value reconstructs what the authors themselves already
combined via the standard formula. **The caveat is inverted relative to
NPL's**, though: NPL's reconstruction (differential polarizability x
independently measured field) took real domain expertise to assemble
correctly; Bothwell's underlying arithmetic (`g/c^2`) is textbook, and the
authors computed it themselves trivially. What this case validates is NOT
the arithmetic but the extended-sample MACHINERY: the per-site geometry,
envelope weighting, and map assembly, producing the right measured-map
slope end-to-end against a published measured map. Does not change the
blind-prediction count (still zero).

### Geometry (Bothwell et al., Nature 602, 420 (2022), arXiv:2109.12238,
B3 ratified with the INFERRED flag)

Magic-wavelength (813 nm) lattice, Gaussian atom-number envelope,
~100,000 atoms, sample spanning ~1-1.3 mm, imaging resolution 6.04 um/pixel.
Two geometric parameters are INFERRED (not directly stated in the
dossier/paper): site spacing 406.5 nm (= 813 nm / 2, the dossier's own
"813/2" cross-check) and the Gaussian envelope's sigma, ~402.7 um
(derived from "two +/-1.5-sigma regions, ~100 pixels each" at
6.04 um/pixel: `sigma = 100*6.04um/1.5`). The script's computational
grid spans +/-3-sigma at the real 406.5 nm spacing (~5900 sites), each a
single motional-ground-state node (the dossier gives no per-site trap
frequency, and this mm-scale gradient does not depend on motional
averaging within a site).

### Coordinate-sign mapping (G9 sign-off gate edit 2)

Bothwell's own z-axis puts LOWER physical positions at LARGER coordinate,
so their published gradient is NEGATIVE while this engine's own height
convention (higher = faster) gives a POSITIVE slope. The script computes
the slope in the engine's own convention and negates it for the
comparison, with the mapping stated explicitly (not left coincidental).

### Method: the REAL per-site pipeline, not a shortcut formula

1. Configure `coupling.type='stark_dc'` with a spatially uniform,
   EXACTLY ZERO field (isolating the gravitational term: Bothwell's
   published corrected slope already has BBR/lattice-light/DC-Stark/pixel
   corrections removed, so it targets the isolated gravitational
   gradient, and this script's own configuration matches that).
2. `environment.gravity.g_m_s2 = 9.796` (Bothwell's own USGS-surveyed
